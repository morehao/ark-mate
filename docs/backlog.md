## 1. 现在就绪（T）

### T1 · O3-a：MCP 全局并发限流/排队

- **现状**：`backend/internal/infra/mcp/pool.go` 按 server 池化、**同会话串行**、有界 + 空闲回收；但
  N 条会话可以同时打到**同一个**远端 server——没有 server 维度的总闸。
- **做什么**：
  1. 在 pool 层加 **per-server 并发上限 + 等待队列**（在途数超过上限时排队，而不是直接拒绝）；
  2. 排队要**有超时**（超时回一个可识别的错误码，不要伪装成上游失败）；
  3. 默认上限必须先定一个值并写进 `docs/decisions.md` 新版本（改默认值会改变延迟特征，
     属于口径变更；**不能**让"未配置"等于无界）。
- **验收（静态 + 行为）**：
  - 单测：N 条会话并发调用同一 server 时，观测到的同时在途数 ≤ 上限；第 N+1 个请求确实**在等**，
    而不是被悄悄丢弃；
  - 单测：排队超时返回明确错误（含 server 与排队时长），且不破坏"同会话串行"；
  - 反证实跑：抽掉信号量 → 并发上限那条单测红。
- **风险**：限流放在 pool 还是 gateway 要一次定清楚（两处都放会得到两个上限，调哪一个都不生效）。

### T2 · O3-b：MCP 调用结果进审计表（事件流第二刀）

- **现状**：`backend/internal/drivers/gateway/source.go` 只在 stderr 留一行
  `(server, tool, outcome, latency_ms)`——**事后无法按会话复盘调用了什么**。
- **做什么**（建议分两刀，别一次做完）：
  1. **第一刀：审计表**。新表（`server_id / tool / outcome / latency_ms / session_id / run_id /
     created_at / error_kind`）+ 迁移 + 写入点（**写失败只 WARN，不阻断调用**——与事件持久化
     C32 同一取舍）+ 保留期/行数上限（否则这张表会无限长）。
  2. **第二刀：事件流**（可选）。新增事件 type 必须同时改三处：事件常量与契约快照
     （`TestEventTypeContractFrozen`）、前端 `frontend/packages/types/src/events.ts`、
     以及"前端是否真的消费"（不消费就别加事件，只留审计表）。
- **验收**：
  - 一次工具调用后，审计表里有且只有一行，字段能对上；写表失败时调用仍成功（WARN 可见）；
  - 迁移可回滚到上一版（按既有迁移约定），历史库升级后旧数据不被改写；
  - 反证实跑：把写表改成阻断调用 → 那条"上游成功但审计失败"的用例红。
- **风险**：审计表若带工具**入参正文**，会把路径/密钥写进库；第一版只记元数据与摘要。

### T3 · L3-1：启动过程显式建模

- **现状**：`frontend/scripts/dev-loop.mjs` 有阶段监督（任一阶段死即整体回红），但缺一张
  「带预算与降级策略的启动步骤表」——启动仍是一串 `await`。
- **做什么**：定义步骤表：每步 `{name, critical, timeout, dependsOn, 降级动作}`；把
  `backend/internal/bootstrap/app` 的启动顺序与 dev-loop 的阶段表**收敛到同一份声明**（两份就是两个真相）。
- **验收**：
  - 守卫（fail-closed）：步骤表存在、每个 `critical` 步骤都有超时与降级动作、步骤依赖不成环；
  - 动态：kill 掉一个非 critical 阶段 → 整体仍能用且诊断里写明降级；kill 掉 critical 阶段 →
    非 0 退出（这条 dev-loop 已有，别退化）。
- **风险**：`backend/internal/bootstrap/app/ready.go` 已经在表达"就绪"；新表若与它各说一套，先合并再谈。

### T4 · L3-3：审计表加哈希链

- **现状**：`backend/internal/adapters/outbound/sqlite/dao/definition_revision.go` 的每条 revision 独立，改过也看不出来。
- **做什么**：加 `prev_hash` / `hash` 两列（写这段时最新迁移是 v30，所以下一版是 v31），写入时在
  **同一事务**里取该表最后一条的 `hash` 作为 `prev_hash`；创世条用固定常量。
  提供一个只读校验函数（遍历链，发现断点返回第一条坏行的 id）。
- **验收**：
  - 单测：写三条 → 链连续；手工改中间一条的正文 → 校验函数定位到它；
  - 单测：并发写两条不会分叉（单进程写入前提；若将来多实例，需先有跨实例锁，见 C26）；
  - 反证实跑：把 `prev_hash` 写死成常量 → 校验单测红。
- **风险**：`hash` 的输入必须**规范化**（字段顺序、时间格式），否则同一内容两次算两个 hash。

### T5 · L3-4：投递与执行解耦（事务性 outbox）

- **现状**：automation 的「跑完」与「结果送达」是同一条路（`backend/internal/domain/automation/carrier.go`）；
  通道投递失败是常态，但失败后没有可重试的持久化队列。
- **做什么**：outbox 表（`id / 目标 / 载荷 / 幂等键 / 尝试次数 / next_attempt_at / 状态`）+
  投递 worker（退避重试）+ 幂等键去重；执行侧只负责"把结果写进 outbox"，投递由 worker 独立推进。
- **验收**：
  - 通道不可用时执行仍成功、outbox 留 pending；通道恢复/重启后**补投且只投一次**；
  - 重复投递按幂等键去重（消费端或发送端二者选一，写清楚）；
  - 反证实跑：把投递移回同步路径 → "通道失败不阻断执行"的用例红。
- **风险**：outbox 不做清理会无限增长；与 T2 的审计表一样要有保留策略。

### T6 · L3-5：注入面的字节预算与截断可回读

- **现状**：进入上下文的正文（系统提示 / skill 正文 / 能力定义）有预算，但超限时的截断提示
  是否带完整路径与可回读定位，**没有统一判据**。
- **先做 30 分钟勘察**（不要硬造）：找出实际存在的注入拼装点；找不到平台侧拼装的那一处，
  就不要为它造预算（那会变成一条空转判据）。
- **验收**：
  - 守卫：注入入口必须带预算参数（无预算的调用点零命中）；
  - 行为：超限必截断，截断提示含**完整路径 + 可回读定位**（文件名 + 行号/锚点），
    用户能照着找回原文；
  - 反证实跑：把截断提示改成"……（已截断）"→ 判据红。
- **风险**：预算值本身是产品口径（改它会改变回答质量），定了就写进 decisions。

### T7 · O4：鉴权 / 多租户（云端 B 段）

- **现状**：`backend/internal/delivery/middleware/credential.go` 只认一个静态 `MATE_TOKEN`（默认空 = 不鉴权，
  仅回环），无用户/角色/审计/限速/轮换；静态资源不鉴权。
- **前提**：B1 身份映射先落地；**不得推翻决策 v3③「单机单操作员」红线**（它是本地形态的前提，
  云端是新增形态，不是替换）。
- **验收**：多身份可区分、越权请求有稳定码、审计能回答"谁在什么时候做了什么"；
  本地形态（无 token、回环）行为**零变化**（有回归用例）。

### T8 · O5：远端接入鉴权（云端 B 段）

- **现状**：`backend/internal/runtime/connect.go` 的 `RemoteSpec` 支持 `headers`，平台不做 OAuth/mTLS；
  HTTP 长流在建会话前会 404（降级记进诊断）。
- **前提**：B2「远程执行面升格」的产品形态先定（会话带 `transport=local|cloud` 那一步）。
- **验收**：凭据不落明文日志；失效凭据有可识别错误；降级路径仍如实进诊断。

### T9 · Windows 出包 + Job Object 进程回收（M4-3）

- **现状**：`Makefile` 的桌面 recipe 只出 macOS；`backend/internal/infra/procreg/procreg_other.go` 在非 unix
  上明确降级（"当前平台不支持进程组信号"）。C26 记的第三子项就等这一步。
- **做什么**：接 Windows NSIS 出包；用 Job Object 重做进程回收（`KILL_ON_JOB_CLOSE`），
  不再依赖进程组信号。
- **验收**：Windows 上杀掉核心 → 子进程树一起退出（无孤儿）；随包载荷路径与
  `desktop_host_path_test` 的"零宿主绑定"判据仍绿。
- **风险**：这是**交付矩阵扩容**，不是一次修 bug；先在 decisions 里登记"Windows 进矩阵"。

## 6. 每完成一项的固定动作

缺任何一步，这一项就不算完成（本仓的取向：**没有判据的纪律等于没有纪律**）：

1. **代码 + 守卫**：至少一条 fail-closed 的静态判据（解析不到即失败），并**实跑反证**——
   故意破坏判据、确认它会红，再复原。反证不能编译通过的不算数。
2. **`docs/agents/guards.md` 的守卫计数 +1**，并在同一段写清"它挡的是哪种静默失效"（照抄现有条目的写法）。
3. **`unimplemented.md`**：从 §2 移进 §3，新 `C` 号 + 关闭依据（提交号 / 决策版本 / 现存路径）。
   §2 只留"决定做但还没做"的条目。
4. **`roadmap.md`**：对应阶段的状态行改成事实（做了就写做了，没做就写没做，别写"进行中"）。
5. **`decisions.md`**：改了口径（默认值、契约、语义）才加新版本；纯实现不写。
6. **commit**：conventional 前缀 + 中文 scope；正文写"为什么"与反证结果。
